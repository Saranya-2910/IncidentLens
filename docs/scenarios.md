# IncidentLens Simulated Incident Scenarios Catalog

This document details the simulated incident scenarios generated by `simulator/generate.py` for evaluating and benchmarking IncidentLens.

Each scenario produces realistic distributed traces, log cascades across microservices, background noise, and realistic multi-line stack traces (Python, Java, Go).

## Detailed Scenario Descriptions

### 1. Database Connection Pool Exhaustion (`db_pool_exhaustion`)
- **Category**: Resource Saturation / DB Connection Pool.
- **Origin Service**: `checkout-service`
- **Cascade Sequence**:
  1. `checkout-service` experiences high connection pool utilization (18/20 connections active).
  2. Thread wait times exceed 5000ms.
  3. Connection pool reaches hard limit: `QueuePool limit of size 20 overflow 10 reached, connection timed out, timeout 30.00`.
  4. Incoming checkout requests block until timing out.
  5. `api-gateway` receives upstream timeouts and returns HTTP 504 Gateway Timeout.
  6. `frontend-service` reports transaction failures to users.
- **Key Log Patterns**:
  - `QueuePool limit of size 20 overflow 10 reached`
  - `connection timed out, timeout 30.00`
  - `HTTP 504 Gateway Timeout`
- **Expected Root Cause**: Checkout service saturated its PostgreSQL connection pool (QueuePool max 20 + overflow 10), preventing new database transactions and causing gateway timeouts.

---

### 2. Redis Out-of-Memory Eviction Failure (`redis_oom`)
- **Category**: Cache / Memory Exhaustion.
- **Origin Service**: `auth-service`
- **Cascade Sequence**:
  1. Redis memory usage reaches 94.2% of 4096MB with `maxmemory-policy noeviction`.
  2. Redis rejects subsequent write commands: `OOM command not allowed when used memory > 'maxmemory'`.
  3. `auth-service` fails to persist or refresh user session tokens.
  4. `api-gateway` fails session validations and responds with HTTP 401 Unauthorized / 500 errors.
- **Key Log Patterns**:
  - `OOM command not allowed when used memory > 'maxmemory'`
  - `Session lookup failed for user token`
  - `Failed to persist user session`
- **Expected Root Cause**: Redis instance memory reached the hard `maxmemory` threshold under a `noeviction` policy, blocking session writes and breaking user authentication.

---

### 3. Bad Deploy / Missing Environment Variable (`bad_deploy`)
- **Category**: Deployment Configuration Error.
- **Origin Service**: `payment-service`
- **Cascade Sequence**:
  1. Rolling update deploys image `payment-service:v2.4.1`.
  2. Application startup fails during settings validation due to missing mandatory environment variable `STRIPE_API_KEY`.
  3. Pydantic validation error triggers immediate container crash.
  4. Container enters `CrashLoopBackOff`.
  5. Inter-service calls from `checkout-service` fail with connection refused; `api-gateway` returns HTTP 502 Bad Gateway.
- **Key Log Patterns**:
  - `1 validation error for Settings`
  - `STRIPE_API_KEY`
  - `Field required`
  - `Deployment v2.4.1 failed to initialize`
- **Expected Root Cause**: Deployment of payment-service v2.4.1 failed to start because the mandatory `STRIPE_API_KEY` environment variable was omitted from the release configuration.

---

### 4. Cascading Downstream Timeout (`cascading_timeout`)
- **Category**: Lock Contention / Thread Starvation.
- **Origin Service**: `inventory-service`
- **Cascade Sequence**:
  1. Heavy concurrent requests trigger database deadlock on table `inventory_locks`.
  2. Transaction rollbacks and lock waiting hold HTTP worker threads.
  3. `order-service` calls to `inventory-service` time out after 5.0 seconds (`httpx.ReadTimeout`).
  4. `order-service` thread pool exhausts, propagating timeouts to `api-gateway`.
- **Key Log Patterns**:
  - `Deadlock detected waiting for table lock 'inventory_locks'`
  - `httpx.ReadTimeout: The read operation timed out after 5.0 seconds`
  - `Cascading timeout: downstream service 'inventory-service' did not respond`
- **Expected Root Cause**: Row-level lock contention and deadlock in inventory-service caused downstream read timeouts (5s) that starved caller thread pools.

---

### 5. Disk Full on Worker / Storage Volume (`disk_full`)
- **Category**: Operating System / Infrastructure Storage.
- **Origin Service**: `worker-service`
- **Cascade Sequence**:
  1. Background Celery worker fills `/var/tmp` filesystem to 98.9% capacity.
  2. Invoice generation task attempts to buffer rendered PDF and fails with `OSError: [Errno 28] No space left on device`.
  3. Task crashes and moves to FAILURE state; subsequent notifications cannot attach invoice files.
- **Key Log Patterns**:
  - `OSError: [Errno 28] No space left on device`
  - `Task generate_invoice_pdf failed`
  - `Failed to write temporary buffer to /var/tmp`
- **Expected Root Cause**: The disk volume hosting `/var/tmp` on the worker instance ran out of free space (Errno 28), aborting PDF export jobs.

---

### 6. Upstream Payment Gateway 503 Outage (`upstream_payment_gateway_503`)
- **Category**: External Upstream Dependency Outage.
- **Origin Service**: `payment-service`
- **Cascade Sequence**:
  1. Third-party payment gateway (Stripe API) starts returning HTTP 503 Service Unavailable.
  2. `payment-service` retries 3 times with exponential backoff before failing.
  3. Circuit breaker trips to OPEN state after consecutive threshold errors.
  4. Checkout requests are immediately rejected with circuit open notices and HTTP 503 responses.
- **Key Log Patterns**:
  - `stripe.error.APIConnectionError: Service Unavailable (HTTP 503)`
  - `Circuit breaker tripped to OPEN state for gateway 'stripe'`
  - `Upstream payment processor returned 503`
- **Expected Root Cause**: External payment processor returned HTTP 503 Service Unavailable, tripping the payment service's circuit breaker to OPEN state.

---

### 7. Memory Leak Leading to Kubernetes OOMKill (`memory_leak`)
- **Category**: Memory Leak / Container Lifecycle.
- **Origin Service**: `recommendation-service`
- **Cascade Sequence**:
  1. Unbounded cache growth in recommendation embedding cache continuously leaks memory.
  2. Garbage collection fails to reclaim memory; usage passes 93% threshold (3840MB / 4096MB).
  3. Host Linux kernel OOM killer terminates process (`exit code 137`).
  4. Container restarts, leading to connection resets at `api-gateway`.
- **Key Log Patterns**:
  - `Memory usage exceeded threshold: 3840MB / 4096MB`
  - `Out of memory: Kill process`
  - `Container recommendation-engine terminated with exit code 137 (OOMKilled)`
- **Expected Root Cause**: Memory leak caused by unbounded cache retention in recommendation-service triggered Linux kernel OOM killer (exit code 137).

---

### 8. TLS/SSL Internal Certificate Expiry (`certificate_expiry`)
- **Category**: Security / Infrastructure PKI.
- **Origin Service**: `auth-service`
- **Cascade Sequence**:
  1. Internal mutual TLS (mTLS) certificate for `auth.internal.corp` reaches expiration timestamp.
  2. Upstream microservices attempting HTTPS RPC connections fail SSL handshake: `urllib3.exceptions.SSLError: [SSL: CERTIFICATE_VERIFY_FAILED] certificate has expired`.
  3. Dependent services cannot verify authentication tokens and fail with 500 errors.
- **Key Log Patterns**:
  - `urllib3.exceptions.SSLError: [SSL: CERTIFICATE_VERIFY_FAILED] certificate has expired`
  - `SSL certificate verification failed for https://auth.internal.corp`
  - `Internal RPC failed: CERTIFICATE_VERIFY_FAILED`
- **Expected Root Cause**: The internal SSL/TLS certificate for auth-service expired, causing inter-service HTTPS verification handshakes to fail.

## Control Datasets (Negative Controls)

### `control_steady_state`
- **Description**: Normal steady-state operation of the microservice fleet.
- **Has Incident**: `false`
- **Expected Root Cause**: `none`
- **Behavior**: Routine HTTP access logs (200, 304), periodic CPU/memory health checks, queue worker debug logs, and benign CDN notices. No errors or failures.

### `control_benign_traffic_spike`
- **Description**: Sudden 650% inbound traffic spike from a flash sale campaign.
- **Has Incident**: `false`
- **Expected Root Cause**: `none`
- **Behavior**: Request rate spikes significantly; Kubernetes HorizontalPodAutoscaler (HPA) triggers scaling from 4 to 16 replicas; worker pods launch and traffic handles smoothly without dropped requests or 5xx errors.
